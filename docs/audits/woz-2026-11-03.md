## Findings détaillés

Format : fichier:ligne · problème · impact · correctif de cinq minutes (ou plan) · référence.

### 🔴 Critiques

#### WOZ-034 Décodage de `versions.json` en tout-ou-rien, puis écrasement
- **Fichiers** : `Stores/VersionStore.swift:39-47` (le `catch` remplace par `VersionManager.makeDefault()`) ; `Models/GameVersion.swift:573` (`decodeIfPresent(GameProfileKind.self, …)` lève une erreur sur une valeur brute inconnue) ; `ViewModels/MainDashboardViewModel.swift:102` (`decodeFailed` ne bloque que la migration) et `:1680` (`persistVersionManager()` sans condition, appelé par `selectVersion`, `setGamePath`, `addVersion`…).
- **Problème** : un seul profil illisible fait échouer tout le fichier. L'app charge alors les défauts, et la première action de l'utilisateur réécrit `versions.json` avec ces défauts.
- **Impact** : multi-générations direct. Un utilisateur crée un profil BfA, puis revient à une version antérieure à `world_of_warcraft_x64` (Sparkle, DMG plus ancien, canal bêta) : tous ses profils personnels et chemins de jeu sont perdus. Le même scénario se reproduira à chaque nouvelle famille.
- **Correctif 5 min** : dans `persistVersionManager()`, `guard !loadResult.decodeFailed else { return }` (garder le drapeau sur le VM), et copier le fichier illisible en `versions.json.corrupt-<date>` avant toute écriture.
- **Correctif de fond** : décodage tolérant profil par profil (`[String: FailableDecodable<GameVersion>]`, les profils illisibles mis en quarantaine dans le fichier et non supprimés) ; `GameProfileKind` avec un cas `unknown(String)` qui se ré-encode à l'identique.
- **Référence** : choix maison.

#### WOZ-036 Les échecs de Wine ne remontent pas
- **Fichiers** : `Services/LaunchService.swift:387-406` (stdout/stderr → `print("[GAME…]")` seulement), `:408-417` (`terminationHandler = { _ in … }` : le statut est ignoré), `:166` (mode Terminal : `processDidTerminate` part tout de suite).
- **Problème** : `launch(version:)` réussit dès que `process.run()` a démarré `/bin/sh`. Un Wine qui sort en erreur (prefix 32 bits pour un client x64, ICD Vulkan absent, KosmicKrisp qui ferme le client, DLL manquante) donne une fenêtre qui ne s'ouvre jamais, sans message ni journal sur disque.
- **Impact** : c'est le premier mode de panne du chantier BfA (#43, #46), et le diagnostic dépend de la sortie console de Xcode.
- **Correctif 5 min** : garder les 64 derniers Ko de stderr dans un tampon circulaire. Dans `terminationHandler`, si `terminationStatus != 0` moins de 30 s après le lancement, publier une `LaunchServiceError.processExited(status, tail)` via `processDidTerminate`, et écrire le tampon dans `~/Library/Logs/WoWSilicon/<profil>.log` (que Troubleshooting pourra joindre).
- **Référence** : choix maison.

### 🟠 Haute priorité

#### WOZ-035 Pipeline par famille dispersé, sans exhaustivité
- **Fichiers (37 sites, 9 fichiers)** : `Views/MainDashboardView.swift` (9 : `:46-49` libellés, `:718-728` liste des modèles et `isStandaloneTemplate`, `:759`, `:765`) · `Services/ConfigService.swift` (6 : `:68`, `:169`, `:197`, `:233`, `:260`, `:286` sur `wowVersion == "1.12.1"`) · `Services/PatchService.swift` (5 : `:38`, `:43`, `:200`, `:223`, `:228`) · `ViewModels/MainDashboardViewModel.swift` (4 : `:129`, `:1081`, `:1515-1524`) · `Views/OptionsView.swift` (3 : `:100`, `:108`, `:148-149`) · `Services/TroubleshootingService.swift` (3) · `Services/TelemetryService.swift` (3 : `:15-23`, qui redéclare le renderer x64) · `Services/PatchingStatusChecker.swift` (2 : `:33`, `:52`) · `Services/LaunchService.swift` (2 : `:194`, `:514`).
- **Problème** : aucun `switch profileKind`. Tous les tests sont des `if x == .worldOfWarcraftX64` / `== .genericD3D9`, et le dernier `else` exécute le pipeline WoW 32 bits. Une 4e valeur de `GameProfileKind` compile sans erreur et part dans `applyGamePatch` 32 bits (exige `DivxDecoder.dll`), `makeShellCommand` 32 bits (`WINEDLLOVERRIDES=d3d9=n`, x87), et les écrans réglages WoW 32 bits. La connaissance « x64 = wined3d + MoltenVK, sans x87 » existe en trois exemplaires (`LaunchService.swift:194-217`, `:544-560`, `TelemetryService.swift:16-19`).
- **Correctif 5 min** : ajouter `extension GameProfileKind { var pipeline: ClientPipelineKind { switch self { … } } }` sans `default`, et faire passer par lui `makeShellCommand` et `applyGamePatch`. Le compilateur devient le garde-fou des futures familles.
- **Correctif de fond** : voir « Cible d'architecture » plus bas.
- **Référence** : choix maison.

#### WOZ-040 Capacités stockées et figées par profil
- **Fichiers** : `Models/GameVersion.swift:433-439` (`supportsVanillaTweaks`, `supportsDLLLoading`, `usesRosettaPatching`, `optimizationLevel`, `executableName` persistés), `:444-450` (d'autres capacités dérivées de `profileKind` : deux sources de vérité), `:586-597` (`syncCapabilities`), `:697-706` (`ensureDefaults` ne resynchronise que les clés de `defaultVersions`), `ViewModels/MainDashboardViewModel.swift:122-135` (`addVersion` copie le modèle tel quel).
- **Problème** : un profil créé depuis le modèle BfA, générique ou une copie de Wrath garde les capacités du jour de sa création. Une correction du modèle `bfa837X64Template` (ex. `supportsDLLLoading` quand #43 apportera un d3d11 maison) n'atteindra jamais les profils existants. `libSiliconPatchSubdirectory` (`:452-458`) et `ConfigService` décident sur la chaîne libre `wowVersion`.
- **Correctif 5 min** : étendre `ensureDefaults` aux profils dont l'id n'est pas un défaut, en resynchronisant les capacités sur `VersionManager.profileTemplates` choisi par `profileKind` (+ `wowVersion`).
- **Correctif de fond** : les capacités deviennent calculées (`pipeline.capabilities`) ; seules les données utilisateur sont persistées. Garder l'encodage des anciens champs pendant une version pour permettre le retour arrière.
- **Référence** : choix maison.

#### WOZ-037 Environnement Wine dupliqué, précédence inversée
- **Fichiers** : `Services/LaunchService.swift:518-539` (32 bits), `:544-560` (x64), `:582-594` (installeur), `:748-764` (lanceur tiers) ; précédence : `:532`, `:558`, `:593`, `:762` (`"\(custom) \(baseEnv)"`).
- **Problème** : quatre copies de la même construction d'environnement en chaîne shell, toutes un peu différentes. Comme `custom` est placé **avant** `baseEnv`, l'affectation de base l'emporte : un utilisateur ne peut surcharger ni `WINEDLLOVERRIDES`, ni `WINE_D3D_CONFIG`, ni `DXVK_ASYNC`, ni `MVK_CONFIG_*`, alors que le champ « Environment » de l'onglet Options le laisse croire. Pour le x64, c'est le seul levier d'expérimentation sur le renderer (#43). `launchInstaller` et `launchThirdPartyLauncher` ne tiennent pas compte de la famille (d3d9 en natif, `WINE_D3D_CONFIG` forcé). C'est inatteignable aujourd'hui pour le x64 (`wantsLauncher` forcé à `false`, `MainDashboardViewModel.swift:129`), mais le risque est latent.
- **Correctif 5 min** : inverser l'ordre en `"\(baseEnv) \(custom)"`, la dernière affectation gagnant (vérifier que `WINEPREFIX` reste filtré, `BundledWineRuntime.swift:126`). Le test de référence 32 bits signalera le changement de chaîne : à mettre à jour volontairement.
- **Correctif de fond** : un `LaunchPlan` en valeur (`executable`, `arguments: [String]`, `environment: [String: String]`, `cwd`) construit par le pipeline et exécuté sans `/bin/sh -c` ; la précédence se fait par un `merge` explicite.
- **Référence** : choix maison.

#### WOZ-038 `MainDashboardViewModel` : objet central et deux modèles de concurrence
- **Fichiers** : `ViewModels/MainDashboardViewModel.swift` (1 832 lignes, 46 `@Published`, 47 `DispatchQueue.global/main`, `Task.detached` en `:1435`, `:1455`, `:1551`) ; `Services/LaunchService.swift:96-104` (`@unchecked Sendable`, `processDidTerminate` et `focusObservation` mutables sans isolation déclarée) ; `Services/ProcessRunner.swift:81-103`, `:157-185` (attente bloquante par sémaphore et `usleep`, sans annulation).
- **Problème** : la classe est `@MainActor` mais déporte son travail par GCD et revient par `DispatchQueue.main.async`, ce qui contourne la vérification d'isolation de Swift 6. Aucune de ces opérations n'est annulable. `ProcessRunner` bloque un thread GCD jusqu'à 120 s (`PatchService.swift:132`). Le ViewModel concentre le cycle de vie de tous les profils, toutes familles confondues.
- **Correctif 5 min** : convertir un seul flux, `applyAudioOutput` (`:931-945`), en `Task { let r = await Task.detached { … }.value; … }` comme le fait déjà `monitorWineProcesses`.
- **Correctif de fond** : `ProcessRunner.run` en `async` (continuation + `withTaskCancellationHandler` → `terminate()`) ; découper le VM par responsabilité (profils, patch, lancement, audio, dépendances).
- **Référence** : choix maison (Swift 6 strict concurrency, convention du `CLAUDE.md`).

### 🟡 Moyenne priorité

#### WOZ-042 Dépatcher en 32 bits supprime un `d3d9.dll` tiers ; patch non transactionnel
- **Fichiers** : `Services/PatchService.swift:240` (`removeIfExists(d3d9.dll)` sans condition) contre `:276-280` (x64 : suppression seulement si identique octet pour octet) ; `:31-101` (une dizaine d'étapes de copie et un `rundll32` Wine, sans retour arrière).

- **Correctif 5 min** : remplacer `:240` par `try removeEmbeddedD3D9DLL(in: gameURL)` (et `:229` pour le générique), comme le fait déjà le x64.
- **Référence** : choix maison.

#### WOZ-041 Un seul prefix Wine pour toutes les générations
- **Fichiers** : `Services/WineRegistrySupport.swift:9-11`, `Services/BundledWineRuntime.swift:77`, `Services/LaunchService.swift:215-217` (refus si le prefix n'est pas WoW64).
- **Problème** : 1.12, 3.3.5, BfA et les jeux génériques partagent un prefix, donc le même registre (Option-as-Alt, Retina, audio, overrides). Le x64 exige `system32` + `syswow64`. Un prefix créé autrement bloque BfA, et la seule issue est de supprimer le prefix entier, au détriment des profils 32 bits.
- **Décision à prendre** : un prefix par famille de pipeline (recommandé : `wow32`, `wow64`) ou par profil. Elle conditionne `WineBottleService` et la migration. La question revient à l'utilisateur, pas à woz.
- **Référence** : choix maison.

#### WOZ-039 Ordre des profils personnels non déterministe
- **Fichier** : `Models/GameVersion.swift:727` (`for (key, value) in versions where !seen.contains(key)`).
- **Impact** : l'ordre d'itération d'un `Dictionary` Swift varie d'un processus à l'autre. Les profils BfA et générique changent de place dans le sélecteur à chaque lancement.
- **Correctif 5 min** : `.sorted { $0.value.displayName.localizedStandardCompare($1.value.displayName) == .orderedAscending }` sur le reste, ou un tableau d'ordre persistant.
- **Référence** : choix maison.

#### WOZ-044 Contrôle d'architecture PE au seul choix du fichier
- **Fichiers** : `ViewModels/MainDashboardViewModel.swift:371-381` (avertissement non bloquant dans `setGamePath`) ; `Services/LaunchService.swift:229-253` (aucun contrôle PE avant le lancement).
- **Problème** : un `Wow.exe` remplacé, ou un profil importé, n'est jamais revérifié ; un exécutable x86 lancé avec le pipeline x64 (ou l'inverse) échoue sans message, ce qui aggrave WOZ-036.
- **Correctif 5 min** : dans `prepareLaunchArtifacts`, `if PEArchitecture.mismatchMessage(for: PEArchitecture.read(from: wowExecutableURL), profileKind: version.profileKind) != nil { throw … }` ; le parseur est déjà pur et testé.
- **Référence** : choix maison.

#### WOZ-050 Lecture disque dans des propriétés lues par le `body` racine
- **Fichiers** : `ViewModels/MainDashboardViewModel.swift:388-395` (`canOpenGameDirectory` : `gameDirectoryURL` puis `fileExists`), `:216-224` (`canOpenLauncherDirectory`) ; `Models/GameVersion.swift:460-507` (`gameDirectoryURL` / `gameExecutableURL` font 1 à 3 `stat()` par lecture).

## Cible d'architecture multi-générations

### Constat de départ
`GameProfileKind` porte bien la notion de famille, mais rien d'autre n'en découle. Chaque service la réinterprète. Les données utilisateur (chemin, réglages) et la définition du pipeline (patchs, environnement, renderer, prefix, capacités) sont mêlées dans `GameVersion`, puis persistées ensemble. La bonne nouvelle : le x64 a montré la forme à suivre (commande à part `makeX64ShellCommand`, statut à part, refus explicite du prefix, tests de référence 32 bits pour prouver la non-régression). Il suffit de la généraliser.

### Cible

```swift
// 1. Le profil persisté ne contient que des données utilisateur.
struct GameProfile: Codable, Sendable {
    var id, displayName: String
    var kind: GameProfileKind          // tolérant : .unknown(String) se ré-encode à l'identique
    var clientBuild: ClientBuild?      // "3.3.5a"/12340, lu par BinaryVersionReader, plus de String libre
    var gamePath, launcherExePath: String
    var common: CommonSettings         // audio, env, HUD, WDB
    var family: FamilySettings         // enum : .wow32(Wow32Settings) / .wow64(Wow64Settings) / .generic(D3D9Settings)
}

// 2. Un pipeline par famille, choisi par un switch exhaustif (sans default).
protocol ClientPipeline: Sendable {
    var capabilities: ClientCapabilities { get }        // addons, realmlist, mods, graphicsConfig, x87, launcher, maturity
    var presentation: PipelinePresentation { get }      // libellés « Executable / Client Check », sous-titre
    var prefixRequirement: PrefixRequirement { get }    // .wow64, .any → sélection du prefix
    func preflight(_ p: GameProfile, _ fs: GameFolderSnapshot) -> [PreflightIssue]   // PE arch, d3d9 obsolète, Vulkan
    func patchPlan(_ p: GameProfile, _ fs: GameFolderSnapshot) -> PatchPlan          // étapes pures + annulation
    func patchStatus(_ p: GameProfile, _ fs: GameFolderSnapshot) -> PatchStatusDescriptor
    func launchPlan(_ p: GameProfile, _ rt: RuntimeLayout) throws -> LaunchPlan     // argv + env dict + cwd
}
extension GameProfileKind {
    var pipeline: any ClientPipeline {
        switch self {
        case .worldOfWarcraft:    Wow32Pipeline()
        case .worldOfWarcraftX64: Wow64Pipeline()
        case .genericD3D9:        GenericD3D9Pipeline()
        }
    }
}

// 3. Exécution unique et observable.
protocol ProcessExecuting: Sendable { func start(_ plan: LaunchPlan) async throws -> WineSession }
struct WineSession { let exit: AsyncStream<WineExit>; let stderrTail: () -> String }
enum WineFailureClassifier { static func classify(_ exit: WineExit, tail: String) -> LaunchServiceError? }
```

### Ce que ça change
- **Ajout d'une famille** (Cata/MoP 32 bits D3D11, Legion+ x64) : un nouveau `case` fait échouer la compilation tant que le `switch` n'est pas complété. Un fichier `XxxPipeline.swift`, une ligne dans `profileTemplates`, et aucun `if` dans les vues.
- **#43 (D3D11 → Metal)** : se loge dans `Wow64Settings.renderer` et `Wow64Pipeline.launchPlan`. Plus de `WINE_D3D_CONFIG` codé en dur dans trois fichiers.
- **Robustesse Wine** : `WineSession` + classificateur transforment les sorties connues en erreurs typées (« 64-bit installation… 32-bit wineserver », ICD absent, `kernel32` introuvable), avec journal sur disque.
- **Testabilité** : `patchPlan`, `patchStatus`, `preflight` et `launchPlan` sont des fonctions pures sur un `GameFolderSnapshot` et un `RuntimeLayout` construits à la main. Les tests de référence existants (`testMakeShellCommandIsIdenticalToMainFor32BitProfiles`, `testPrepareLaunchOutputForWoWAndGenericMatchesMainReference`) deviennent les tests de non-régression de `Wow32Pipeline`. Plus de dépendance au prefix réel ni à `Bundle.main`.
- **UI** : `MainDashboardView` / `OptionsView` lisent `capabilities` et `presentation` ; les 15 ternaires de famille disparaissent.

### Chemin de migration (chaque étape se livre seule)
1. **Garde-fous** (≤ 1 jour) : WOZ-034 (persist bloqué + décodage tolérant), WOZ-036 (statut + stderr), WOZ-043. Aucun changement de forme.
2. **`switch` exhaustif** : `GameProfileKind.pipeline` ; déplacer `makeShellCommand` / `makeX64ShellCommand` derrière `Wow32Pipeline.launchPlan` / `Wow64Pipeline.launchPlan`, en gardant les tests de référence verts sans y toucher.
3. **Capacités calculées** : `ClientCapabilities` dérivé de la famille et de `clientBuild`. Les champs stockés restent encodés une version de plus (retour arrière), puis sont retirés (WOZ-040).
4. **`LaunchPlan` en valeur** + `ProcessExecuting` + fin de `/bin/sh -c` (WOZ-037, WOZ-048), puis `ProcessRunner` en `async` (WOZ-038).
5. **`PatchPlan`** transactionnel (WOZ-042), puis **prefix par famille** (WOZ-041, après décision de l'utilisateur).
